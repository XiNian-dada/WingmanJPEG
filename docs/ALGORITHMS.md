# Algorithms and implementation

## Exact constant blocks

The `Screen` pixel encoder uses the same libjpeg-turbo accurate integer path,
quality tables, 4:4:4 sampling and entropy settings as `Standard`. The only
upstream modification is an opt-in branch in `src/jcdctmgr.c`, generated by
[`build.rs`](../build.rs) in Cargo's private build directory. It is enabled only
when the compressor carries this wrapper's marker and uses `JDCT_ISLOW`.

For an 8×8 component block whose 64 samples all equal `s`, the normalized DC
coefficient is `8 * (s - 128)` and every AC coefficient is zero. With DC quantizer
`q`, the final coefficient is:

```text
dc = 8 * (s - 128)
quantized_dc = sign(dc) * floor((abs(dc) + floor(q / 2)) / q)
quantized_ac[1..63] = 0
```

[`flat_core.h`](../flat_core.h) precomputes DC results for all 256 sample values
per eligible quantization table. Every sample is checked; a single differing
sample selects the original DCT/quantization path. On ARM64 the comparisons use
NEON, with a first-row early exit for many textured blocks. Other architectures
use scalar comparisons.

Per component, a 64-block probe with fewer than 8 constant blocks triggers a
960-block cooldown. Whole cooldown batches bypass the detection branch. Missing
a constant block during cooldown costs speed only: the reference encoder still
produces the same coefficients. Detection is per JPEG call, not a cross-frame
cache, and no frame-difference or delta protocol is used.

## Coefficient-domain recompression

`Coefficient` reads JPEG's quantized coefficients, avoiding IDCT, pixel color
conversion and FDCT. Each target quantizer is `max(requested, source)`, so it
never pretends to recover precision already discarded by the source encoder.
For source coefficient `c`, source quantizer `old` and chosen quantizer `d`:

```text
n = abs(c) * old + floor(d / 2)
new_coefficient = sign(c) * floor(n / d)
```

Blocks with all 63 AC coefficients zero only need DC requantization. Other
blocks use [`requant_core.h`](../requant_core.h): scalar integer division on
non-ARM64 targets and eight-lane NEON on ARM64. The vector kernel precomputes
`r = ceil(2^31 / d)`, estimates the quotient with `SQDMULH`, and subtracts one
when the estimate times `d` exceeds `n`. Divisor 1 is handled explicitly.

The admitted domain is `1 <= old <= d <= 255` and the full signed 16-bit
coefficient range. Here `n < 2^24`, so the estimate is exact or one too high and
one correction yields exact integer division. Signed minimum values retain
their unsigned magnitude correctly. See the linked historical research and
ARM tests in [BENCHMARKS.md](../BENCHMARKS.md).

These coefficients match the scalar coefficient-domain formula. Requantization
can still lose image detail, and its output need not match pixel re-encoding.
Source sampling is retained; a quality number alone is not a matched-rate or
matched-quality comparison. Unsupported source tables/color spaces fall back
to `Screen` before coefficient processing.

## Source preservation and entropy optimization

`Preserve` retains source coefficients and quantization values, then asks
libjpeg-turbo to build optimized Huffman tables. No coefficients are
requantized. Color output adds no quantization loss; grayscale keeps only luma,
which intentionally removes color. EXIF and ICC markers are retained within
the documented marker limits, except color ICC markers in grayscale output.

The quality field is ignored by this mode but must still be in 1–100 because
the public options are validated before processing. Unsupported formats return
an error instead of silently changing image precision. Output bytes differ
from the source even when decoded pixels match. A statistics pass adds cost;
smaller files and faster processing are not guaranteed.

## Error and allocation boundary

[`native.c`](../native.c) owns `setjmp`/`longjmp`, codec callbacks and a heap
cleanup context. No jump crosses a Rust frame. Each call owns its codec state;
malformed frames return an error, and subsequent frames can still be processed.
The Rust owner frees successful C buffers through the originating C API after
copying their bytes. Processing and size limits are documented in the README;
they do not bound total memory for a whole application or all concurrent calls.
